# 암호화 백업 실행과 확인

## 운영자가 처음 실행할 명령

프로젝트 폴더의 본인 터미널에서 실행한다. Node.js 22 이상, Docker Desktop, 설치된 Supabase CLI 로그인이 필요하다. `.env.local`에는 기존 운영 URL과 서버 키가 있어야 한다. 키를 새로 붙여 넣거나 출력할 필요는 없다.

```powershell
npm run backup:create
```

화면에 표시되지 않는 복구 암호를 두 번 입력한다. 16자 이상의 긴 문구를 사용하고, 암호는 채팅·명령 인자·환경변수·백업 폴더에 저장하지 않는다. 암호 관리 도구 등 백업과 다른 곳에 별도 보관한다. 암호를 잃으면 복구할 수 없다. 프로그램은 TTY 터미널에서만 암호를 받으며 입력 파이프나 자동 암호 주입을 지원하지 않는다.

수집 중에는 주보·사진 편집을 잠시 멈춘다. 대상은 `zefnxczgwpsmfcixonpb`로 고정되어 있다. 백업 완료 후 **암호화·복호화·저장 해시 검증 완료**와 `.dgcb` 파일 경로가 표시되어야 한다. CLI 로그인/DB 접근 오류가 나면 완료가 아니며, 암호나 키가 담긴 원시 로그를 채팅에 올리지 않는다. 로그인 복구는 본인 터미널의 공식 CLI 흐름을 사용하고 DB 비밀번호를 임의로 재설정하지 않는다.

기본 PC 보관 위치는 프로젝트의 `.local/backups`이며 Git에서 제외된다. 이 스크립트는 운영 DB·사진을 수정하거나 새 클라우드 프로젝트를 만들지 않는다. 운영 DB 복원·자동 배포·Drive 업로드도 실행하지 않는다.

## 수집 범위와 누락 방지

- 운영 DB는 공식 CLI의 역할·스키마·COPY 데이터·별도 마이그레이션 이력 SQL을 수집한다. 원격 ref를 항상 명시한다. Auth 사용자 및 Storage 객체 메타데이터와 마이그레이션 이력이 빠지면 파일 생성을 거절한다.
- 사진은 private `bulletin-images`의 실제 WebP를 목록 페이지마다 내려받는다. 이 앱의 UUID.webp 규칙 외 폴더/파일이 있으면 생략하지 않고 중단한다. 다른 버킷은 수집 범위에 포함되지 않는다.
- 앱 6개 테이블·버킷 설정·사진 목록을 수집 전후 비교한다. DB 이미지 참조에 파일이 없거나 파일 크기가 바뀌면 중단한다. 편집 중 변경이 감지되면 다시 실행한다.
- 원본 마이그레이션 SQL과 소스 커밋, 앱 자료 및 사진 목록도 암호화 안에 포함한다. 공개 키·서버 키·DB 비밀번호·Vault 루트 키는 백업 파일에 별도로 복사하지 않는다.
- Auth 프로젝트 설정, 초대 복귀 URL, Vercel 변수 값, 새 Supabase 클러스터의 기본 역할/서비스 설정은 자동 복원 범위가 아니다. 운영 복구 안내를 따라 별도 확인한다.
- 여러 SQL 내보내기는 하나의 공통 DB 트랜잭션 스냅샷이 아니다. 전후 비교가 모든 Auth/세션 동시 변경까지 검출하는 것은 아니므로 수정 중단과 복구 검수가 필요하다.

현재 형식은 **원본 파일 합계 64 MiB, JSON 96 MiB, 최대 10,000개 항목**까지 지원한다. 앱 인벤토리는 16 MiB까지다. 초과하면 부분 백업을 완료로 저장하지 않고 거절한다. 향후 사진 자료가 커지면 스트리밍 형식으로 확장해야 한다.

로컬 연습은 `npm run backup:local`로 실행한다. 고정 로컬 Docker DB의 public/private/auth/storage/extensions와 마이그레이션 이력을 custom-format 덤프로 수집하고, 암호 없는 역할 정의와 사진 파일을 함께 넣는다. 운영 SQL 백업과 로컬 custom-format 덤프의 복원 명령은 다르다.

## PC 파일 검증

생성 시 파일을 암호화한 후 메모리에서 복호화·모든 파일 SHA-256 대조, 저장 후 암호화 파일 SHA-256 대조를 자동 실행한다. 암호와 평문 SQL/사진을 임시 파일로 쓰지 않는다. JavaScript 프로세스 메모리·OS 스왑까지 안전하게 지워진다는 보장은 아니다.

같은 폴더의 `.dgcb.receipt.json`은 파일명·크기·SHA-256·생성 대상·검증 여부만 담는다. 복구 암호·SQL·사진·계정 내용은 없다. 암호화 파일과 영수증을 함께 보관하되 영수증만으로 복구할 수는 없다.

나중에 다시 확인:

```powershell
npm run backup:verify -- ".local/backups/실제파일명.dgcb"
```

## Google Drive 보관과 두 사본 확인

보관 폴더: [꿈꾸는좋은교회 · 암호화 백업](https://drive.google.com/drive/folders/1EMVqTfnEl--CmFS0KdR9BEqyWHrpmWfz).

1. 검증 성공한 `.dgcb`와 내용 없는 검증 영수증만 올린다. 평문 SQL, 풀어 놓은 폴더, `.env`, 복구 암호를 올리지 않는다. 기존 공유 권한을 확대하지 않는다.
2. 업로드 성공 응답과 Drive 파일 크기·파일명·부모 폴더를 재조회한다.
3. Drive의 암호화 파일을 다른 로컬 파일명으로 다시 내려받아 PC 원본과 SHA-256을 비교한다. 가능하면 복구 암호로 다시 검증한다.

```powershell
node scripts/backup.mjs check-copy ".local/backups/원본.dgcb" ".local/backups/다시받은사본.dgcb"
```

`check-copy`는 서로 다른 두 로컬 파일의 바이트만 확인한다. Drive 업로드 자체를 증명하거나 자동 수행하지 않으며 결과도 `copyBytesVerified`로 기록한다. 실제 Drive 위치·메타데이터 확인까지 끝나야 두 보관소 완료로 WBS에 기록한다. 원본과 동일 경로를 비교 대상으로 지정할 수 없다.

## 복구 파일 열기와 운영 복원 구분

먼저 생성된 암호화 파일을 인증·검증하고, 필요할 때만 새 로컬 복구 폴더로 푼다. 기존 폴더·심볼릭 링크·기존 파일을 덮어쓰지 않는다. Drive에 동기화되는 곳으로 평문을 해제하지 않는다.

```powershell
node scripts/backup.mjs unpack ".local/backups/실제파일명.dgcb" --output ".local/recovery/첫복구확인"
```

평문 복구 위치는 `.local/recovery`의 새 직계 하위 폴더로 제한된다. 상위 경로는 사용자 본인이 관리하는 신뢰할 수 있는 로컬 폴더여야 하며 심볼릭 링크로 동기화 폴더에 연결하지 않는다. Windows 접근 권한은 사용자 폴더 권한을 별도로 확인한다. POSIX 파일 모드가 NTFS 권한을 대신하지 않는다.

잘못된 암호·변조된 데이터는 파일을 쓰기 전에 거절한다. 파일 해시·크기·상대 경로·중복 이름·Windows 특수 경로를 검사한다. 해제했다고 운영 DB에 자동으로 복원하지 않는다. 별도 격리 검수를 먼저 수행하고 담당자가 운영 대상·복구 시점·자료 손실 범위를 확인한 뒤 공식 Supabase 절차로 복구한다.

확인이 끝나면 평문 복구 폴더를 정리한다. 일반 파일 삭제가 SSD 보안 삭제를 보장하지는 않는다. 실제 DB·사진 복구와 게시/권한 검수는 `operations-recovery.md`를 따른다.

## 파일 형식 · 버전 1

추가 라이브러리 없이 Node.js 표준 crypto를 사용한다. `.dgcb`는 일반 ZIP이 아니다.

- 헤더 36바이트: ASCII `DGCBKP01` 8바이트 + 무작위 salt 16바이트 + 무작위 IV 12바이트.
- scrypt: N=131072, r=8, p=1, 32바이트 키, maxmem=256 MiB.
- AES-256-GCM, 헤더 전체를 AAD로 인증, 마지막 16바이트가 인증 태그. 암호화마다 새 salt와 IV를 쓴다.
- 평문은 gzip 압축된 UTF-8 JSON이다. 버전·메타데이터와 파일별 상대 경로/바이트 수/SHA-256/base64 본문을 포함한다. 복호화 시 출력 크기를 제한한다.

장기 보관 시 이 문서와 복구 프로그램도 소스와 함께 보존한다. 형식 변경 시 기존 버전의 복구 지원을 유지해야 한다.
