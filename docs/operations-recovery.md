## 무엇을 백업해야 하는가

| 대상 | 포함할 내용 | 복구 시 확인 |
| --- | --- | --- |
| 앱 DB | 주보/블록/공지·일정/교회 안내/이미지 참조/운영자 멤버십, private 함수, RLS·권한·제약조건 | 비공개 항목·초안 비노출, 운영자만 수정 |
| Auth | 사용자·인증 관련 자료와 프로젝트 인증 설정 | 세션 정책, 가입 제한, 초대/비밀번호 복귀 주소, 실제 운영자 로그인 |
| Storage | 버킷 설정·객체 메타데이터 **및 실제 WebP 파일** | 경로/파일 수/크기/해시와 DB 참조, private 유지 |
| 이력·소스 | 마이그레이션 6개와 적용 이력, 커밋·잠금 파일 | 같은 버전으로 재현, 이력 불일치 방지 |
| 서비스 설정 | Vercel 변수 이름/대상/키 버전, Supabase URL·인증 설정, 배포 ID·별칭·리전 | DB URL과 공개/서버 키가 같은 프로젝트 소속인지 확인 |

DB 덤프는 Storage 파일 자체를 포함하지 않는다. Free 프로젝트는 별도 정기 내보내기와 외부 보관이 필요하다. DB 복구와 사진 복구를 항상 한 세트로 관리한다. 현재 원격 객체 0개라는 사실은 사진 백업 기능을 검증했다는 뜻이 아니다.

키의 실제 값·DB 비밀번호·Auth 토큰은 이 문서/Notion/검사 로그에 기록하지 않는다. 서비스 키는 서버 전용이며 NEXT_PUBLIC 변수로 옮기지 않는다. 루트 암호화 키가 필요한 Vault/암호화 컬럼을 향후 도입한다면 별도 키 복구 절차도 추가한다.

## 운영 백업 실행 순서

1. 담당자가 수정 작업을 잠시 멈추고 대상 ref가 `zefnxczgwpsmfcixonpb`인지 확인한다. 덤프와 파일 복사 중 변경이 있으면 같은 백업 세트로 간주하지 않고 다시 수집한다.
2. 설치된 CLI의 `supabase db dump --help`를 먼저 확인한다. 이번 확인 버전은 3.1.0이며 기본 대상은 로컬이다. 원격은 반드시 `--remote=zefnxczgwpsmfcixonpb`로 명시한다. 비밀번호를 명령문/채팅에 넣거나 비밀번호를 재설정하지 않는다.
3. 공식 가이드에 따라 역할·스키마·데이터와 `supabase_migrations` 스키마/데이터를 내보낸다. 관리 스키마 auth/storage의 서비스 기본 객체와 앱이 추가한 정책은 구분하고 앱 정책은 저장소 마이그레이션으로 재현한다. CLI가 생략하는 범위를 실제 출력에서 확인한다. `--data-only --use-copy`를 사용하는 자료 내보내기와 스키마 내보내기는 별도다.
4. Storage API로 버킷의 실제 파일을 모두 내려받아 원래 경로·크기·SHA-256 목록을 만든다. 파일 누락 또는 읽기 실패가 하나라도 있으면 완료 처리하지 않는다. `.env` 파일을 무조건 통째로 자료 백업에 섞지 않는다.
5. 암호화 수단을 정한 뒤 전체 세트를 인증된 암호화 형식으로 잠그고 복호화·해시 대조를 수행한다. 평문 임시 자료는 동기화되지 않는 제한 폴더에만 두고 검증 후 정리한다. SSD에서 일반 삭제가 보안 삭제를 보장한다고 간주하지 않는다.
6. PC와 별도 개인 보관소에 같은 암호화 세트를 복사하고 해시를 대조한다. 백업 시각·커밋·마이그레이션·파일 수·DB 범위·암호화 형식·검증 결과만 업무 기록에 남긴다.

첫 운영 내보내기·암호화 파일 생성·Drive 보관과 사본 검증까지 완료했다. DB 연결 비밀번호를 채팅으로 제공받거나 재설정하지 않았다. 복구 암호도 사용자 기기의 보호된 입력으로 설정했으며 전달받지 않았다.

## 실제로 통과한 로컬 복구 연습

실행:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/test-restore.ps1
```

고정 로컬 컨테이너 `supabase_db_dreaming-good-church`만 사용한다. 원격 주소나 복구 대상을 받는 옵션은 없다. `postgres` 원본은 읽기만 하고, `church_restore_` 뒤 무작위 32자리 이름의 별도 DB를 만들어 복구한 뒤 삭제한다. 개발 서버를 중지하거나 원본 로컬 DB를 초기화하지 않는다. 작업 중 로컬 편집이 있었다면 원본 비교가 실패하므로 편집을 멈추고 다시 실행한다.

- public/private/auth/storage/extensions/supabase_migrations 범위를 custom-format 덤프로 복원했다. 기존 로컬 클러스터 역할을 사용했으며 새로운 클러스터 역할/암호 복구 연습은 아니다.
- **47개 테이블 내용 해시·건수**, 정책 정의, 테이블/컬럼 권한, 소유권, 앱 함수와 마이그레이션 이력을 비교해 일치를 확인했다. ACL 나열 순서 차이는 정규화하여 실제 권한을 비교한다.
- 복원 DB 안에서 가상 자료를 넣어 익명 공개 항목만 읽기, 초안/비공개 차단, 익명 쓰기 차단, 비운영자 차단, 운영자 읽기·게시 함수 실행, 멤버십 회수 후 차단을 확인했다. 가상 자료는 트랜잭션 롤백했다.
- 실행 전후 원본 내용·권한 해시가 같았다. 복구 DB와 임시 덤프를 삭제했다. 최초 수동 확인용 DB·덤프도 정리했고 남은 복구 연습 DB 수는 0개였다.
- 원본 DB에서 검증 SQL을 실행하면 자료를 넣기 전에 거절하는 보호 장치도 확인했다.
- 성공 시 민감한 내용 없이 `.local/restore-drill/result.json`에 범위·일치 여부·시간만 남긴다. 이번 복구 검증은 약 5.27초였으며 실제 장애 전체 복구 시간은 아니다.

이 연습은 실제 원격 백업 복원, Storage 파일 복구, 로그인 서버 전환, 브라우저 전체 재검수를 대체하지 않는다. 소유권·기본 스키마 충돌을 확인하여 로컬 전용 관리자 역할로 복구했다. 이 관리자 역할 사용법을 호스팅 프로젝트에 그대로 적용하지 않는다.

## DB 장애 대응과 복구

1. 발생 시각·영향 범위와 마지막 정상 배포/백업을 기록하고 담당자에게 알린다. 쓰기 작업과 자동 게시를 중단한다. 삭제나 덮어쓰기 전에 현재 상태도 보존한다.
2. 인증/배포 문제인지 실제 자료 손실인지 구분한다. DB 손실이 없다면 먼저 앱·변수·권한 문제를 복구한다.
3. 백업을 별도 격리 환경에서 열고 자료·RLS·함수·이미지 참조를 확인한다. 추가 클라우드 프로젝트는 별도 결정 없이 만들지 않는다. 실제 운영 덮어쓰기는 대상/시점/자료 손실 범위를 담당자가 확인한 뒤 수행한다.
4. DB와 사진의 같은 시점 세트를 복구하고, 마이그레이션 이력과 권한을 대조한다. 로그인/세션과 프로젝트별 키도 확인한다. 사진 경로를 바꾸면 참조까지 맞춘다.
5. 공개 목록·비공개/초안 차단·공개 PDF·이미지·관리자 저장·게시/취소를 검수한 뒤 쓰기를 재개한다. 사고 원인·복구 시각·유실 범위·재발 방지를 기록한다.

## Vercel 배포 되돌리기

현재 정상 검수 기준점은 위 Preview 배포다. **삭제한 임시 DB에 연결했던 과거 검수 배포로 별칭을 되돌리지 않는다.** 같은 코드라도 빌드 당시 환경변수와 DB 연결이 다를 수 있다. URL만 정상 배포처럼 보이는 것으로 판단하지 않는다.

정식 운영 출시 전에는 정상 Production 배포 ID와 해당 환경변수/DB 호환성을 따로 기록한다. 현재 Preview 검수 기준점을 Production Instant Rollback 대상으로 간주하지 않는다. 실제 운영 롤백은 아직 실행하지 않았다.

운영 사고 시 대시보드 프로젝트의 Production Deployment → Instant Rollback에서 실제 대상 도메인·이전 정상 배포·DB 호환성을 확인하고 실행한다. 완료 후 공개 화면/API와 관리자 흐름을 다시 확인한다. CLI를 쓸 때도 설치 버전의 `vercel rollback --help`와 로그인 권한을 먼저 확인한다.

- Instant Rollback은 이전 빌드로 도메인을 돌리는 작업이다. DB 자료/스키마·Storage·현재 프로젝트 설정을 함께 되돌리는 기능이 아니다.
- Hobby에서는 바로 이전 Production 배포로 롤백할 수 있다. 과거 임의 배포 복귀가 항상 가능한 것으로 가정하지 않는다.
- 이전 배포는 이전 환경변수를 사용할 수 있다. 삭제된 DB 연결, 만료/회전된 키, 새 스키마와의 호환성을 먼저 확인한다.
- 롤백 후 Production 도메인 자동 할당이 중단된다. 문제를 고친 정상 배포를 검수하고 다시 Promote한 뒤 자동 할당 복구까지 확인한다.
- 파괴적 DB 마이그레이션을 코드 롤백과 함께 무작정 역실행하지 않는다. 운영 변경은 가능한 경우 기존 코드와 호환되는 추가 → 새 코드 검수 → 불필요한 구조 정리 순서로 분리한다.

## WBS 42의 남은 완료 조건

1. 백업 주기·보존 정책·암호 오프라인 메모 보관 수단은 사용자 확정 완료. 반복 실행/사본 정리는 수동 운영이며 실제 메모 작성·보관은 사용자가 관리한다. 암호화 방식·PC/Drive 위치·첫 백업 및 두 사본 검증은 완료.
2. 실제 운영 백업 세트의 SQL 실행 복구 연습은 완료. 가상 사진을 포함한 로컬 암호화 세트 DB·사진 복구도 별도로 통과했다. 실제 HTTP 서비스 복구와 운영 전환은 아래 검수에서 구분한다.
3. 실제 관리자 원격 로그인·복귀 주소·Production 변수/도메인/첫 정상 기준점 확정 완료. 실제 운영 자료/사진 업로드 등 최종 콘텐츠 검수는 남아 있다.
4. 정상 A/B의 실제 운영 롤백·Promote 복귀 및 단계별 검수 완료. 연락 이메일·대체 담당 미지정도 사용자 확정 완료다. WBS42의 위 기준은 충족했으며 실제 운영 콘텐츠·인쇄·최종 출시 검수는 WBS43으로 이어간다.
