주 구분은 한국 시간 월요일~일요일로 하고, 백업이 있는 최근4개 주에서 마지막 검증 사본을 하나씩 보관한다. 생성 시각과 실제 SHA-256을 기준으로 같은 사본을 구별한다. Drive에서 다시 받은 파일명은 달라도 같은 해시이면 별도 백업으로 세지 않는다. 실패/불완전 사본은 보존 개수 충족으로 세지 않는다.

실행은 npm run backup:create 후 PC 암호화·복호화·해시 검증, 같은 파일의 개인 Drive 업로드, 재다운로드 해시 대조까지 한 세트다. PC에서 생성만 했으면 외부 보관 완료가 아니다. 정리할 때는 새 사본 검증과 양쪽 보관 목록을 먼저 대조하고, 보존 집합 밖 파일/영수증만 담당자가 직접 정리한다. 이번 정책 반영에서는 삭제·자동 정리·Drive 권한 변경을 하지 않았다.

예를 들어 같은 날5번 백업해도 마지막7개와 주별 마지막4개의 합집합을 남긴다. 한 주의 마지막 사본이 최근7개에도 포함되면 하나만 센다. 편집하지 않은 날에는 정기 생성 의무가 없지만 배포·대량 수정 전 백업은 별도로 수행한다. 이미 검증한 동일 자료가 있는 경우에도 작업 직전 자료/설정 변화 여부를 확인한다.

오프라인 메모는 사용자가 직접 관리한다. 보관 수단은 확정했지만 메모 작성/실물 보관 완료를 원격으로 확인한 것은 아니다. 문서화만으로 암호 복구 가능 여부를 보증하지 않는다. 복구 목표 시간/허용 자료 손실 시간은 아직 별도 수치로 확정하지 않았다.

현재 암호화 파일은 DB·Auth 자료·사진 파일·이력을 포함하며 Auth 프로젝트 설정, Vercel 변수 값/키, DB 비밀번호는 포함하지 않는다. 이 설정들은 승인된 별도 보관 수단과 설정 문서를 따라 복구한다. 새 백업을 만들었다고 이 제외 항목까지 보존했다고 기록하지 않는다.

## 롤백 훈련 적용안 — 실행 승인 전

정상 A 하나만 있는 지금 바로 롤백하면 이전503 배포로 갈 수 있다. 동일 소스의 정상 Production B를 하나 만든 후 **A → B → A로 롤백 → B를 Promote** 순서로 검증하는 안이다. Hobby의 바로 이전 Production 제한을 충족하면서 화면/DB 구조의 버전 차이를 만들지 않는다. 같은 코드를 쓰므로 서로 다른 앱/스키마 버전 간 호환성을 증명하는 훈련은 아니다.

이 안은 실제 운영 도메인을 여러 번 전환하고 Production 빌드1회를 추가한다. 기존 유료 요금제/새 Supabase 프로젝트/키/보호/DB/Auth 설정/게시 자료/PR 병합은 변경하지 않는다. 새 결제나 요금제 변경이 필요하면 실행하지 않는다. 작업자가 운영 자료를 편집하지 않는 시간에 순차 실행한다. 주일 오전은 제외한다.

1. A의 고정 소스·CI·도메인 대상·변수/DB 이력·최근 백업 상태를 확인한다. 마지막 검증 사본 이후 자료/설정 변화가 있으면 먼저 새 백업을 준비한다. 이전 백업이 현재 자료 전체를 보장한다고 가정하지 않는다.
2. 동일 ff5cb98, Production 변수3개, Node24/icn1로 B를1회 생성한다. READY와 소스/지역을 확인하고 운영 도메인이 B를 가리키는지 get_alias로 기록한다. 빌드 실패 시 A를 유지하고 중단한다.
3. B에서 공개 목록200·없는 자료404·비로그인 쓰기401·주요 화면 및 기존 Preview/보호 유지 확인. 핵심 검수 실패면 A로 복귀하고 실패를 기록한다. B가 불량이면 마지막 Promote 대상으로 사용하지 않는다.
4. A가 바로 이전 정상 Production 롤백 후보인지 확인하고 request_rollback(A)를1회 요청한다. 도메인의 실제 대상이 A가 될 때까지 확인하고 기본 응답을 재검수한다. 동작이 끝나기 전 다음 전환을 보내지 않는다.
5. 검증된 B를 request_promote(B)로 복귀시켜 롤백 상태를 해제한다. 별칭 매핑 성공·도메인 B·기본 응답을 확인한다. 이후 Git push 자동 배포 연결/차단 규칙 자체까지 검증한 것으로 간주하지 않는다.
6. 전환별 요청/완료 시각·대상 ID·SHA·HTTP/권한·Preview·DB 건수/이력 유지 결과를 기록한다. 성공하면 B가 현재 정상, A가 이전 정상 기준점이다.

API 도구의 get_project에는 rollbackInfo 옵션이 없어 lastAliasRequest 상태 필드를 볼 수 없을 수 있다. 이 경우 일반 get_project의 null만으로 전환 완료를 판정하지 않고 get_alias 실제 대상·배포 상태·HTTP·promote 별칭 결과로 확인한다. 409 등 진행 중 충돌은 중복 요청으로 해결하지 않는다. 권한/매핑 실패가 반복되면 자동으로 다음 전환을 실행하지 않고 현재 정상 대상을 보존해 보고한다.

## 중단·복구 기준

B 빌드/검수가 실패하면 정상 A를 유지/복귀한다. A로의 롤백이 실패했지만 B가 계속 정상이고 도메인도 B이면 상태를 보존하고 실패를 보고한다. 롤백 성공 뒤 B Promote에 실패하면 정상 A를 유지하면서 필요한 대시보드 조치를 구체적으로 안내한다. 정상 B로 돌아오지 못한 상태를 훈련 완료로 기록하지 않는다. 어떤 경우에도 초기503 배포로 임의 이동하거나 DB/사진/키/Auth를 되돌리지 않는다.

이전 배포에 들어 있는 환경변수는 현재 프로젝트 변수 변경으로 갱신되지 않는다. 실제 장애에서는 코드와 DB·키 호환성을 확인한 뒤 대상과 복구 방법을 판단한다. 이 훈련은 DB 백업 복원과 별개다.

## 진행 기록

운영 정책은 위 사용자 선택대로 확정했다. 적용안 작성 시점에는 훈련 준비만 했고 이후 사용자가 별도로 실행 승인했다. 새 백업/Drive 검증 후 B 생성·A 롤백·B Promote와 단계별 검수를 완료했다. 이전의 '첫 배포 실패 시503으로 철회' 승인을 재사용하지 않았다.
