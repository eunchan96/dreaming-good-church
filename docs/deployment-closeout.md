# 배포 마무리와 후속 개선 분리 · 2026-11-13

사용자가 기능은 정상이며 원문 전사·UI/인쇄 디테일은 배포 완료 후 단계적으로 개선하겠다고 결정했다. 11/1 초안의 실제 내용을 검증된 자료로 게시하지 않는다. 전체 전사 재검토와 인쇄 넘침을 후속 작업으로 기록하고 지금은 배포 설정·소스 통합을 우선한다.

## 확인한 운영 상태

- 기본 주소 https://dreaming-good-church.vercel.app, 정상 Production B=dpl_ASfp6HvCMXUz79hSuyEb6ssPwbAv / ff5cb98, 이전 정상A=EMpc. 배포/API·PC/모바일·실제 관리자·동일 소스 롤백 근거는 기존 문서에 있다.
- 사용자가 Supabase Site URL을 기본 운영 주소로 전환했고 원격 읽기로 확인했다. 기존 localhost callback·고정 검수 account·운영 account redirect3개는 유지한다. 키/가입 정책/기타 Auth 설정을 변경한 것으로 기록하지 않는다.
- 미게시 초안1개/26항목/게시0개, 공개 API/PDF 비노출 유지. 원문 정확성·실물 인쇄를 출시 설정 완료의 근거로 쓰지 않는다.
- 통합 PR9는 develop 대상 Draft이며 main/develop은 아직 초기63d3c5e다. 이후 소스는 ff5cb98과 같고 문서만 추가했다. 사용자 미커밋 이슈 자동화 수정은 포함하지 않는다.

## 소스 반영 실행안

1. 최종 통합 PR9의 소스/변경 파일·CI 성공을 확인한다. 사용자 승인 후 Draft 해제와 merge commit으로 develop에 반영해 작업별 커밋을 보존한다. 원격 develop이 예상과 달라졌거나 충돌이 있으면 임의 덮어쓰지 않는다.
2. 병합 후 develop 결과와 기존 검증 소스의 차이가 문서뿐인지 재확인하고 develop→main 출시 PR을 작성한다. 이 PR에서도 CI를 확인한 뒤 같은 승인 범위에서 merge commit으로 반영한다. 새 기능·스키마·설정 변경이 끼어들면 승인 범위를 갱신한다.
3. main/develop 반영이 Vercel 자동 배포를 발생시키는지 관찰한다. 정상 B를 임의로 바꾸지 않으며 자동으로 새 배포가 생성되면 커밋/환경/리전/별칭과 공개 응답·초안 비노출를 확인한다. Git 연동의 자동 배포 동작은 아직 검증됐다고 가정하지 않는다.
4. 자동 배포가 없다면 현재 정상 B를 유지하고 main의 앱 코드와 B의 ff5cb98이 일치함을 기록한다. 문서/merge commit SHA가 다르다는 이유만으로 불필요한 Production 재배포를 하지 않는다. 별도 재배포가 필요해지면 배포 전 백업 정책을 먼저 따른다.
5. 병합/CI/운영 주소·초안 비노출·Auth URL 재확인 결과를 WBS43에 남긴다. 일반 홈페이지 배포 마무리와 실제 주보 게시/인쇄품질 완료는 구분한다.

PR9→develop 및 이어지는 동일 코드 develop→main 병합은 이 문서 작성 시점에는 실행 전이다. 이전 배포/롤백 승인을 병합 승인으로 재사용하지 않고, 위 구체적인 두 단계 반영을 묶어 확인한다. 브랜치 삭제·과거 작업 PR 일괄 종료·보호 해제·게시·새 DB/유료 자원 생성은 포함하지 않는다.

## 후속으로 넘긴 일

- 실제 주보 원문 전체 재검토: 지정3곳에 한정하지 않고 이름·문구·일정·금액·구조를 원본과 대조한다. HWP 확보 후 원본 기반 작업은 기존 TODO를 유지한다.
- PC/모바일 홈페이지와 관리자 UI의 색·간격·정보 배치 등 디테일 개선. Figma 시안 선행을 필수로 두지 않는다.
- 인쇄2/4면 넘침 경고 해결·표지/약도·A4가로 반접지/A5 4면 실물 검수. 경고를 숨기거나 잘린 인쇄를 정상 처리하지 않는다.
- 실제 주보 공개 게시와 성도용 사진/PDF 본문 검수는 검토된 자료와 별도 게시 확인 후 진행한다.

사용자 결정에 따라 WBS43의 이번 배포 완료 범위는 운영 주소/Auth·마이그레이션·기본 관리자/성도 조회·초안 비노출·소스 반영 확인이다. 전사 정확도/UI·인쇄품질/실제 콘텐츠 게시 확인은 후속 작업에 연결하며 검증 완료로 바꾸지 않는다.
