# 교회 홈페이지 운영 안내

2026-11-13 기준. 운영 주소는 [꿈꾸는좋은교회](https://dreaming-good-church.vercel.app), 입력은 [주보 관리](https://dreaming-good-church.vercel.app/admin/bulletins)에서 한다. 이 문서는 일상 운영의 시작점이며 상세 복구/개발 절차는 끝의 연결 문서를 따른다.

## 지금 사용할 수 있는 범위

주보 작성·지난주 복사·저장·게시/취소, 공지/일정·교회 정보·이미지 관리와 공개 읽기/PDF·설치/오프라인 기능이 구현되어 있다. 원문 정확도·최종 UI·인쇄 레이아웃·실물 인쇄는 후속 개선 중이다. HWP 자동 가져오기는 아직 사용할 수 없다.

11월1일44호는 사진 전사 검토가 끝나지 않은 **미게시 초안**이다. 전사 오류와 인쇄 넘침이 보고되어 있으므로 검증된 실제 주보처럼 게시하지 않는다. 공개 목록이 비어 있는 현재 상태는 장애가 아니다. 기능 구현/로컬·배포 검수와 실제 주보 품질 확인을 구분한다.

## 이번 주 주보 작성

1. 등록된 운영자 계정으로 로그인한다. 공개 회원가입으로 운영 권한을 얻는 방식은 제공하지 않는다.
2. 보관함의 이전 주보를 열고 다음 주 복사 기능으로 새 날짜·호수를 정한다. 원본은 유지한다. 처음 시작하면 ‘+ 새 주보 작성’을 사용한다. 같은 날짜 주보를 중복 생성하지 않는다.
3. 새 주보는 처음에 ‘초안 저장’을 누른다. 이후 입력을 멈추면 자동 저장된다. 화면이 ‘저장됨’인지 확인한다.
4. 예배 순서·본문/설교 제목·담당·공지·일정·헌금 대상월을 확인한다. 반복 공지도 날짜/이름/금액은 다시 확인한다. 첫째·셋째 주 오후예배 등 실제 일정은 원본/교회 일정과 대조한다.
5. 각 항목의 웹 공개 여부를 검토한다. 기본값은 공개다. **웹 비공개 항목도 관리자 인쇄에는 포함**되므로 인쇄물을 전달할 대상도 확인한다. 항목 삭제는 웹/인쇄 양쪽에서 제거하는 별도 동작이다.
6. ‘이번 주 확인 필요’ 항목은 실제 내용을 대조한 뒤 확인 처리한다. 게시 버튼을 활성화하려고 미확인 내용을 일괄 확정하지 않는다.
7. ‘웹 미리보기’로 공개 항목을, ‘인쇄 미리보기’로 내부 항목까지 확인한다. 넘침 경고가 있으면 인쇄 품질 검수 완료가 아니다. 현재 개선 중인 레이아웃은 경고를 무시해 사용하지 않는다.

저장 실패/로그인 만료 시에는 현재 입력을 먼저 보존하고 같은 계정으로 다시 로그인한다. ‘저장 다시 시도’ 후 ‘저장됨’을 확인한다. 충돌 안내가 나오면 다른 창의 최신 내용을 확인한 뒤 다시 연다. 실패 상태에서 새로고침/브라우저 종료만 반복하지 않는다.

## 게시와 게시 취소

게시 전 날짜/호수·확인 필요 항목·웹 공개/개인정보·사진 설명을 검토하고 저장을 완료한다. **‘주보 게시’는 즉시 공개**한다. 미래 날짜라도 바로 공개되며 예약 게시는 아직 없다. 게시할 내용의 권한과 정확성을 확인한 후 진행한다.

게시 후에는 로그아웃한 별도 창에서 [공개 주보](https://dreaming-good-church.vercel.app/bulletins)를 열어 해당 날짜·본문·공개용 PDF를 확인한다. 관리자의 인쇄 미리보기와 성도용 공개 PDF는 서로 다른 범위다.

수정/철회는 다음 순서다.

1. 해당 주보를 열어 ‘게시 취소’를 선택한다. 게시된 주보는 직접 수정하지 않는다.
2. 초안으로 돌아오면 새 공개 조회/PDF에서 제외되었는지 확인한다.
3. 내용을 고치고 저장·공개 범위를 재검토한 뒤 필요할 때 다시 게시한다.

이미 내려받은 PDF·스크린샷·오프라인 저장본은 게시 취소로 원격 회수되지 않는다. 민감한 내용이 잘못 공개됐으면 새 게시를 중단하고 담당자에게 알린다. 웹 화면만 지워졌다고 사고 대응을 종료하지 않는다.

## 공지·일정·사진

[공지·일정 관리](https://dreaming-good-church.vercel.app/admin/community)에서 별도 메뉴 노출이 필요한 내용만 관리한다. 주보의 반복 공지가 별도 공지로 자동 등록됐다고 가정하지 않는다. 제목·공개 상태·게시 시작/종료를 확인하고, 일정은 행사 시간과 게시 기간을 구분한다. 입력 시간은 한국 기준이다.

[교회 정보 관리](https://dreaming-good-church.vercel.app/admin/church)에서 안내 정보를 수정한다. 사진은 실제 필요한 설명과 함께 등록하고 해당 공개 항목에서 어떻게 보이는지 확인한다. 사용 중인 이미지는 삭제가 제한된다. 실패 시 다른 이미지/자료를 임의로 지우지 않는다.

오프라인 저장은 공개 내용만 대상으로 한다. 중요한 수정 뒤에는 성도에게 온라인에서 다시 저장하도록 안내할 수 있지만, 실제 안내 발송은 담당자가 별도로 판단한다. 이전 검수 주소에 설치한 앱과 정식 주소의 저장 공간은 다르다.

## 계정과 비밀정보

계정·일회용 초대/재설정 링크는 운영 담당자만 관리한다. 비밀번호·서버 키·복구 암호·.env.local·계정 링크 HTML을 채팅, GitHub, Notion, Drive 백업 폴더에 올리지 않는다. 백업 폴더에는 암호화 백업과 검증 영수증만 보관한다.

새 운영자 초대/기존 운영자 재설정이 필요할 때만 [계정 안내](deployed-accounts.md)의 명시 Origin 명령을 사용한다. 이 도구는 메일을 자동 발송하지 않는다. 비밀번호를 바꾸기 위해 기존 계정을 불필요하게 재초대하지 않는다. 작업 후 로그아웃한다.

## 백업: PC 생성부터 Drive 확인까지

확정한 시점은 **편집한 날 작업 종료 후 + 배포·대량 수정 직전**이다. 수동 실행이며 예약/알림/자동 삭제는 설정하지 않았다. 복구 암호는 백업과 분리한 오프라인 메모로 본인이 관리한다.

1. 수정 작업을 잠시 멈추고 프로젝트 폴더의 본인 터미널에서 실행한다. 숨겨진 입력에 기존 복구 암호를 직접 넣는다.

```powershell
npm run backup:create
```

2. ‘암호화·복호화·저장 해시 검증 완료’와 새 .dgcb 경로를 확인한다. 오류가 있으면 완료가 아니다. 이 단계는 **PC 사본만 생성**하며 Drive 업로드는 하지 않는다.
3. 해당 .dgcb와 검증 영수증을 [기존 개인 Drive 폴더](https://drive.google.com/drive/folders/1EMVqTfnEl--CmFS0KdR9BEqyWHrpmWfz)에 보관한다. 공유 권한을 늘리지 않는다. 평문 SQL/사진·암호를 올리지 않는다.
4. Drive 파일을 다른 파일명으로 PC에 다시 내려받고 다음 명령으로 원본과 비교한다. 실제 파일명을 넣는다.

```powershell
node scripts/backup.mjs check-copy ".local/backups/원본.dgcb" ".local/backups/Drive에서다시받은사본.dgcb"
```

5. 원본/사본 해시 일치와 Drive 위치/파일 크기를 확인한 뒤 두 사본 보관 완료로 기록한다. check-copy만으로 실제 Drive 저장 위치까지 확인한 것은 아니다.

보존은 최근7개 + 주별 마지막 사본4개의 합집합이다. 한국 시간 월~일 기준 백업이 있는 최근4개 주를 사용하고 같은 사본은 중복 계산하지 않는다. 새 사본 검증 후 담당자가 직접 정리하며, 영수증만 남기고 암호화 파일을 지우지 않는다. 이번 안내 작성으로 사본을 삭제하지 않았다.

복구 연습은 Docker가 실행 중일 때 **Drive에서 받은 파일 경로를 명시**해 실행한다. 암호는 기기에서 직접 입력한다.

```powershell
npm run backup:restore-check -- ".local/backups/Drive에서다시받은사본.dgcb"
```

‘실제 백업 SQL 복구·자료/권한 검증 완료. 임시 컨테이너 제거 완료.’를 확인한다. 이는 격리 복구 연습이며 운영 DB를 덮어쓰지 않는다. 실제 장애 복구는 아래 절차로 담당자가 판단한다. Auth 프로젝트 설정·Vercel 변수/키·DB 비밀번호는 이 백업의 자동 복원 대상이 아니다. 파일 규모가 현재 도구 한도64MiB를 넘으면 백업은 중단되므로 실패를 완료로 처리하지 않는다.

## 장애가 나면

우선 담당과 복구 판단은 본인, 연락은 taegwon02@gmail.com이며 대체 담당은 당분간 미지정이다.

1. 발생 시각·주소·오류 문구·영향 범위를 남기고 편집/새 게시를 멈춘다. 비밀번호/키가 담긴 원시 로그는 전달하지 않는다.
2. 단순 빈 공개 목록, 로그인 문제, 앱 오류, 자료 손실을 구분한다. 현재 초안만 있는 공개 빈 목록은 정상이다.
3. 삭제/초기화/옛 백업 덮어쓰기 전에 현 상태와 마지막 정상 배포·백업을 확인한다.
4. 앱 문제는 검증된 이전 정상 배포와 DB/키 호환성을 보고 롤백한다. 현재 검증 기준점은 B=ASfp/이전A=EMpc이며 실제 실행 전 최신 대상을 다시 확인한다. 문서의 오래된 ID를 그대로 실행하지 않는다.
5. 자료 손실은 [상세 복구 절차](operations-recovery.md)에 따라 격리 복구를 먼저 검증한다. 코드 롤백은 DB·사진 복구가 아니다.
6. 복구 후 공개/비공개·관리자 저장·게시/취소·사진/PDF·백업을 재확인하고 재개 여부를 판단한다.

## 정기 점검 권장안

아래는 운영 권장 체크리스트이며 새로운 자동 일정이나 알림을 설정한 것이 아니다.

- 작업 종료 때: 저장 상태, 미게시/게시 상태와 공개 범위, 새 백업의 PC/Drive 두 사본 검증, 로그아웃.
- 주1회: 공개 홈페이지와 관리자 로그인, 최근 백업 날짜/실제 파일/영수증/사본 일치, 공개 공지/일정 기간, 미해결 오류 확인.
- 월1회와 주요 변경 전: 격리 복구 연습 필요성 및 [Supabase](https://supabase.com/dashboard/project/zefnxczgwpsmfcixonpb)·[Vercel](https://vercel.com/eunchan96s-projects/dreaming-good-church)의 사용량/청구/알림·권한·키 관리 상태 검토. 결제/요금제 변경은 담당자가 판단한다. 숫자 한도와 요금은 실행 시 대시보드 기준으로 확인한다.
- 배포 때: 최종 커밋·CI·대상/도메인·최근 백업·복귀 기준 확인. main 병합만으로 자동 배포되었다고 가정하지 말고 실제 배포 ID/별칭을 확인한다.
