# 운영 SQL 백업의 격리 복구 확인

## 실행

프로젝트의 본인 터미널에서 다음 명령을 실행하고 백업 생성 시 정한 복구 암호를 입력한다. 암호는 화면에 표시되지 않으며 채팅으로 전달하지 않는다.

```powershell
npm run backup:restore-check
```

기본 대상은 `.local/backups`의 검증 영수증으로 확인한 최신 **Drive 재다운로드 사본**이다. 원본 해시와 다른 파일은 거절한다. 특정 SQL 형식 백업을 지정하려면 다음과 같이 한다.

```powershell
npm run backup:restore-check -- ".local/backups/실제SQL백업파일.dgcb"
```

Docker Desktop과 이 프로젝트의 로컬 Supabase가 실행 중이어야 한다. 로컬 DB의 서비스 기본 스키마/역할과 동일한 PostgreSQL 이미지를 사용하므로 이미지를 새로 내려받지 않는다. Docker 연결은 로컬 named pipe/Unix socket만 허용하며 원격 Docker endpoint는 거절한다. 이 명령은 `.env.local`을 읽지 않고 운영 서버 키·DB 비밀번호도 요구하지 않는다.

로컬 전용 custom-format `database.dump` 백업은 이 명령 대상이 아니다. 운영 백업의 `schema.sql`·`data.sql`·역할·이력 SQL 세트를 실제 실행하는 검증이다. 암호 오류·누락·인벤토리 불일치는 복구 컨테이너를 만들기 전에 거절한다.

## 복구 환경과 자료 취급

백업 자료를 기존 개발 DB에 넣지 않는다. 기존 로컬 DB에서는 역할 정의(비밀번호 제외)와 관리 스키마 DDL만 읽는다. SQL 복원 대상은 매번 무작위 이름의 **새 컨테이너와 새 DB**다.

- 네트워크 없음, 호스트 포트 없음, 호스트 바인드/영구 볼륨 없음.
- 읽기 전용 루트 파일시스템, PostgreSQL 자료는 크기가 제한된 `/tmp` 메모리 파일시스템에만 저장.
- 비root 사용자, 추가 권한 차단, CPU 1개/메모리 512MiB/프로세스 수 제한.
- 컨테이너 로그 드라이버 비활성화. SQL과 계정·주보 내용은 사용자 출력/보고서에 포함하지 않음.
- 복호화된 SQL은 파이프로 컨테이너에 전달하며 호스트 평문 파일로 풀지 않음.

복구 암호·SQL·계정 값은 기록하지 않지만 프로세스 메모리나 OS 스왑의 안전한 삭제까지 보장하는 것은 아니다. 사용자 본인이 관리하는 기기에서 실행한다.

## 확인하는 내용

1. SQL의 COPY 구간별 테이블 행 수를 계산하고 실제 복구 결과와 비교한다. 앱 테이블뿐 아니라 Auth·Storage·마이그레이션 이력도 포함한다.
2. 앱 6개 테이블의 실제 자료를 암호화된 백업 인벤토리와 대조한다. 값이 다르면 원문을 출력하지 않고 실패 처리한다.
3. COPY의 트리거 비활성화로 참조 오류가 숨지 않도록 외래키를 다시 생성·검증한다.
4. 복구된 마이그레이션 버전과 백업에 보관된 마이그레이션 파일 목록을 비교한다.
5. 앱 RLS 6개와 익명 공개 항목 읽기·초안/비공개 차단·익명 쓰기 차단·비운영자 차단·운영자 읽기/게시·멤버십 회수 후 차단을 시험 자료로 검증한 뒤 롤백한다.
6. 사진 접근 정책은 로컬 부트스트랩의 사본을 그대로 쓰지 않고, 백업에 들어 있는 앱 마이그레이션에서 복구한다. 사진 수·참조와 아카이브 안 파일 해시도 검증한다.

Supabase의 관리 기본 구조는 로컬 스택에서 준비하고 앱 스키마·자료·이력은 백업 SQL에서 복구한다. 초기 세션은 역할 부여자의 정합성을 위해 `supabase_admin`으로 만들며, 중복 역할 생성만 생략한다. Auth 기본키 등 관리 제약조건을 앱 외래키보다 먼저 준비하고, 앱 사진 정책은 앱 스키마 뒤에 적용한다. 기본 `vault` 확장 구조와 `supabase_realtime` publication도 필요하다. Vault 자료나 루트 키를 복사하지는 않는다.

이 검증은 완전한 클라우드 이전이나 실제 Auth HTTP 로그인/초대 복귀 URL·Storage HTTP 서비스·Realtime·운영 도메인 전환을 검증한 것이 아니다. 관리 서비스 버전·프로젝트별 인증 설정과 키는 별도 검수한다. 사진 HTTP 복원은 기존 로컬 암호화 백업 통합 검증과 구분한다.

## 결과와 정리

성공 시 다음 문구가 나와야 한다.

> 실제 백업 SQL 복구·자료/권한 검증 완료. 임시 컨테이너 제거 완료.

`.local/restore-check/result-무작위값.json`에는 백업 해시·검증 시각·테이블/계정 수·검증 여부·정리 여부만 기록한다. 이메일·사용자 ID·SQL·암호는 없다. 모든 확인과 컨테이너 제거가 끝나기 전에 성공 보고서를 쓰지 않는다.

성공·SQL 실패·일반 Ctrl+C 취소 모두 고유 이름과 생성 라벨을 확인한 뒤 이번 컨테이너만 제거한다. Docker 엔진 중단이나 프로세스 강제 종료로 정리가 불가능한 경우 성공으로 처리하지 않는다. 다음 읽기 명령으로 남은 대상을 확인할 수 있다.

```powershell
docker ps -a --filter label=church.restore-drill
```

정리 오류가 있다면 대상 이름/라벨을 확인한 뒤 해당 시험 컨테이너만 정리한다. 기존 Supabase 컨테이너를 삭제하거나 초기화하지 않는다.

## 검증 이력

2026-11-13: 실제 로컬 SQL 내보내기 세트로 별도 컨테이너의 자료·권한·외래키·이력 검증을 통과했다. SQL 실행 오류를 의도적으로 넣은 경우에도 실패를 보고하고 시험 컨테이너를 제거함을 확인했다. 실제 운영 사본의 사용자 암호 입력 검증 결과는 실행 후 추가한다.
